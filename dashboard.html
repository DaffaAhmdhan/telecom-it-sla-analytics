Telecom & IT Service SLA Incident Analytics

Built around patterns I observed handling network downtime at Telkom ASO and field support in Sukabumi: analyzing 5,000 incident tickets (Nov 2025 – Oct 2026) to see why SLA compliance stalled below 80%.

Key Takeaway (In Plain English)

Why is overall SLA stuck at 79.3%? First, P2 - High tickets actually breach SLA more often (77.13%, 292 breaches) than P1 - Critical (83.87%) because teams jump on P1 immediately while P2 queues silently cross their 8-hour window. Second, Sukabumi pulls the regional average down at 74.17% SLA (18.49h MTTR) due to technician travel distance, while Depok hits 81.68%. Fixing fiber/UPS redundancy and staging local spares in Sukabumi directly targets 41.35% of all breaches.

SQL Methodology & Window Function Queries (from sql/schema_and_kpis.sql)

Raw CSV logs are loaded into SQLite (fact_tickets) via src/run_analysis.py. Month-over-month SLA drift uses LAG() over monthly CTEs, and root-cause concentration uses a cumulative window sum for Pareto 80/20 ranking: 

-- Pareto (80/20) Analysis of SLA Breaches by Root Cause
WITH breach_counts AS (
    SELECT root_cause, COUNT(*) AS breach_count
    FROM fact_tickets
    WHERE sla_met = 0
    GROUP BY root_cause
),
total_breaches AS (
    SELECT SUM(breach_count) AS total FROM breach_counts
)
SELECT
    b.root_cause,
    b.breach_count,
    ROUND(100.0 * b.breach_count / t.total, 2) AS pct_of_breaches,
    ROUND(100.0 * SUM(b.breach_count) OVER (ORDER BY b.breach_count DESC) / t.total, 2) AS cumulative_pct
FROM breach_counts b
CROSS JOIN total_breaches t
ORDER BY b.breach_count DESC;
